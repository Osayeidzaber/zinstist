## Anubis observations

- The JAR claims Minecraft 1.21.11, Java 21+, Fabric, client-only operation, GPL-3.0-only, and bundles Fabric API components plus ImGui Java and platform native archives. Embedded ImGui 1.90.0 native archives contain a Windows DLL (SHA-256 `5f0cb2709a97043f8de42fc3bfb9d2f84808448dc9c605c8aac635b955dc6c24`), Linux `.so` (`3198e517a37d36fad7a8c3c928cae2ee6f71f2401dbc374731f8a4d9770060ef`), and macOS `.dylib` (`da6db90baec7f227a06fbf38fc4b776558548f742899706460afd5cf1660d59a`). They were hashed from nested archives, not loaded or executed.
- String/API inspection found network-related code for Mojang profile/skin endpoints, LRCLIB lyric lookup, Spotify artwork/media integrations, and webhook sending. Webhook transport is configured by a URL in Anubis configuration; that capability can send client-generated alert payloads to the configured endpoint. These are observable integrations, not proof of credential theft.
- CFR 0.152 output shows `EarlyBuildCheck` calls `OfficialBuild`, which reads the containing JAR and validates signed entries against a certificate SHA-256 fingerprint embedded in `BuildConfig`; on a mismatch it routes to `TamperStop`, which starts a Java child using the same JAR to display a warning and then exits. This appears to be anti-tamper behavior, not persistence or command execution. The JAR signature itself was not cryptographically verified in this environment. Decompiled output is imperfect and is not equivalent to original source.
- Spotify classes contain OS helper-process and process-enumeration references, plus JNA native loading; the decompiled methods show `osascript` commands limited to querying/controlling Spotify and a generic platform helper runner with a timeout and forced termination. `ScriptedPlayer` also performs HTTPS album-art GETs based on media metadata. These are feature-linked behaviors, though their complete safety still depends on runtime inputs and bundled native code.
- Recovered architecture includes a Java `ClientModule` base with typed settings, IDs, categories, lifecycle-managed event listeners, enabled-state tracking, and a registry; a reflection/MethodHandle event bus; a Fabric client initializer; an ImGui-based screen/render stack; HUD layout/config stores; and separate module groups. Recovered names show 20 combat, 17 movement, 47 render, and multiple client/misc modules, including an explicitly Donut-focused macro category. The project remains Java-based, so Java is the sensible implementation language.
- The supplied Anubis archive still has no original Gradle/Maven build project or verified source checkout. CFR recovery was not buildable as emitted; a separate Vineflower pass also produced compile errors. Static analysis has not become a method-by-method security proof.
- The scanned class strings did not reveal browser profile/cookie locations, Minecraft account token filenames, Discord token stores, wallet/password-manager paths, or a fixed remote payload host. Absence from string/reference scans does not rule out computed, encrypted, or indirect access.
- The user has authorized Anubis as the development starting point. Its static risk classification remains **Insufficient evidence**; this authorization does not establish a malware-free verdict. The recovered source remains review-only and is excluded from the Jilaton build. Jilaton reuses the observed Java module/settings/lifecycle architecture as a design reference and currently has a separate implementation. Full Anubis source review, endpoint-flow tracing, native dependency review, and provenance matching remain incomplete.
